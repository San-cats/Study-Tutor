# 07 多 Agent 协作（stage06）

## ① 认知颠覆：Agent ≠ API 账号

Agent 拆开只有三样：**代码（循环/工具）+ system 提示词（人格）+ 记忆（账本）**——没有一样是账号。

- 模型是发动机，API key 是钥匙——**一把钥匙养一万个 Agent**
- 计费按 token，和 Agent 数量无关；多供应商只是优化（省钱分层/容灾/特长分工），不是门槛

## ② 调度权移交：Python 退居电话总机

| | stage04 路由器 | stage06 多 Agent |
|---|---|---|
| 谁决定派谁 | 分类器输出 JSON，**Python 查 DISPATCH 表** | **主管 Agent 自己决定**，工具调用请求 |
| 子系统 | 函数 handle_xxx | **Agent**（自己的大脑+账本） |
| 派活方式 | 函数调用 | 自然语言："帮我算一下 3+5" |
| 上下文 | 公共大账本 | **一人一本账**（人格隔离） |

**分类器叛变的终极解法**：让每种人格住进独立的身体——主管上下文里只有主管对话，专家上下文里只有专家的活。

## ③ 主管-专家模式（orchestrator-workers，行业最常用）

```
用户 → 主管Agent（接待+派活）→ 专家Agent（各自干活）→ 主管汇总 → 用户
```

- 主管循环 = 工具循环，**一行新原理都没有**——多 Agent 全是旧零件的新组合
- **工具参数从"数据"变"消息"**：`add(a=3,b=5)` → `ask_math_expert(task="3+5等于多少")`；专家返回的也不是 `"8"` 而是**一句话**
- **自然语言 = Agent 间的通信协议**
- 分派表模式第四次登场：`tool_function` 的值是两个 Agent 函数

## ④ 信息分层：三层人，两道墙

用户只和主管说话；专家只和主管说话；主管账本里只有"任务+专家答复"——**专家的施工记录留在专家自己的账本里**。验收方法：打印两个账本，互不相通（MATH 4 条 vs KNOW 2 条，多出的 2 条是连体婴儿施工记录）。

## ⑤ 主管 system 提示词四件事（五零件再应用）

手下名单（各自擅长什么）→ 派活规则（闲聊亲自答、一题可多派）→ 转述规则（不暴露派了谁）→ 示例。

## ⑥ 多 Agent 对路由器的核心超越

**一题多意图**：分类器一题只能选一个，主管一题可调兵遣将。实战验证："算6+8，再查RAG"一条消息连派两个专家，答案分节汇总。

## ⑦ 本课踩的坑

- append 一次只记一条账（传 2 个参数 TypeError）
- **system 是工牌不是对话**：挂函数外当常量，每次拼在 messages 最前面，不进账本
- "只算一次"的东西别塞回函数体（每次调用烧 9 次 embedding 的回归坑）
- 环境变量名错一个字 = 没钥匙（DEEPSEEK_KEY → DEEPSEEK_KEY_KEY 找茬，对账法：两串并排逐字比）
- **循环依赖**：A import B 且 B import A → partially initialized module；**工具箱不认识使用者**，依赖方向单向
- 灰色 import = 死代码（搬家忘删的行李，PyCharm 灰色当雷达用）
- **连线题**：工具名出现三处（SYSTEM 示例 / schema 的 name / 分派表的 key）——schema 和分派表是一对钥匙锁，改一处查三处，否则 KeyError
